# v0.5 Booking Storage — Consolidated Architecture Proposal

Status: simplified proposal awaiting approval. Documentation only; this document does not authorize implementation.

Baseline: booking domain foundation `2f9faa0`, Expo SDK 57 (`~57.0.27`), React Native `0.86.3`, strict TypeScript. Existing v0.4 screens and fixtures remain unchanged. Every record described here is fictional. Never access, import, or connect to the real desktop Hub or its database.

## Recommended scope

Use local Expo SQLite for bookings, booking history, migration versions, and one-time fictional seed tracking. Keep `src/data/clientRecords.ts` and `src/data/dogRecords.ts` as the single source of truth for clients and dogs in v0.5. Do not create duplicate editable SQLite client/dog records.

Defer the identity registry, quarantine table, database triggers, and repair workflow. Reading a booking must never move, delete, or modify its stored record. Invalid rows remain in place and are returned as explicit diagnostics alongside valid bookings.

Later install `expo-sqlite` through `npx expo install expo-sqlite`; SDK 57 documentation lists it as supported in Expo Go. Use one app-sandbox database (`k9-demo.db`), one connection owner, parameterized queries, a serialized write queue, and `withExclusiveTransactionAsync`. All statements within an exclusive transaction must use its transaction object. Enable foreign keys for history relationships and WAL only after schema compatibility checks. [Expo SDK 57 SQLite documentation](https://docs.expo.dev/versions/v57.0.0/sdk/sqlite/)

## Tables and integrity boundaries

| Table | Important columns and rules |
|---|---|
| `bookings` | `id TEXT PRIMARY KEY NOT NULL`; `dog_id`; `service_code`; `status TEXT NOT NULL` default `confirmed`, restricted to `confirmed`/`cancelled`; `time_zone`; `schedule_kind`; scheduled start/end dates and times; separate actual arrival/departure dates and times; positive integer `revision`; created/updated UTC timestamps. |
| `booking_history` | Event ID, booking FK, operation type, before/after revisions, UTC timestamp, before/after row snapshots. Available from the first migration. |
| `schema_migrations` | `version INTEGER PRIMARY KEY`, `applied_at_utc TEXT NOT NULL`. Sole schema-version authority; no duplicate `user_version`, names, checksums, or retry metadata. |
| `seed_history` | `seed_key TEXT PRIMARY KEY NOT NULL`, `applied_at_utc TEXT NOT NULL`. A versioned key such as `v0.5-demo-001` identifies the exact fictional seed set. |

Booking content columns are nullable at the storage boundary so incomplete historical rows can remain representable. New creates, edits, and restores must produce fully validated canonical bookings. This is not permission for the application to create incomplete bookings.

SQL enforces identity uniqueness, supported status, and revision integrity. Schedule, dog, service, timezone, date/time, and observation rules belong to full TypeScript validation. Avoid SQL content checks that would be reevaluated on a status-only UPDATE and prevent cancellation of malformed records. No triggers are needed. Index booking dog/status/date lookup columns; overlaps remain warnings, never uniqueness constraints.

There is no dog foreign key in v0.5 because dogs are bundled TypeScript records. Build a known-dog-ID set from those records and validate it for every create/edit/restore and stored-row mapping. Test that dog and client IDs are unique and every dog's `clientId` resolves. IDs must not be renamed or removed without a reviewed data migration; display labels can change independently. No persisted copy of client contact information is needed.

A future version may introduce clients/dogs tables in a versioned transaction, preserving existing IDs and importing only the approved fictional records. Validate all booking references before introducing foreign keys; unresolved references must cause an explicit upgrade error and rollback, never deletion or reassignment. The transition of the single source of truth must be approved and implemented across consumers together.

## Domain mapping and invalid records

A pure row mapper returns a validated canonical booking plus separate storage metadata, or a structured diagnostic containing record ID (when usable), field/error codes, and observed status. It must validate raw values before trusting them. Revision and audit fields are not canonical domain fields.

| Schedule kind | Canonical mapping |
|---|---|
| Overnight | Scheduled start date/time → `checkIn`; scheduled end date/time → `checkOut`. |
| Daycare | Equal scheduled dates → `date`; times → `dropOffTime`/`pickupTime`. |
| Training | Equal scheduled dates → `date`; times → `startTime`/`endTime`. |

Validate both stored boundaries before reconstructing a same-day schedule. Preserve actual observations separately; departure-only observations remain supported. Early departure never erases scheduled dates/times, changes service, or releases the original interval for conflict warnings.

Keep the approved six codes and mappings: `dog_boarding`, `dog_daycare`, `board_and_train` belong to Boarding & Care; `private_training`, `puppy_training`, `behaviour_training` belong to Training. Board & Train does not trigger appointment overlap warnings solely because it is a stay.

The canonical domain boundary rejects unsupported fields, including `startDate`. Only the explicit, tested v0.4 fictional seed converter translates the known legacy fixture shape. The row mapper explicitly separates known storage metadata; unexpected booking-content fields must be diagnosed rather than silently normalized. No general legacy importer or raw-payload store is introduced.

Validate rows independently so one malformed record cannot abort checks of others. Return every invalid-record diagnostic without altering its row. Do not present invalid rows as canonical bookings or as conflict-free records. Confirmed or unknown-status invalid records make active conflict checking incomplete; a reliably cancelled invalid row remains visible but does not imply an active conflict. Diagnostics cannot be hidden by calendar-date filtering when their dates are unusable.

A whole-database read failure blocks saving and produces a storage error. It must not be represented as an empty schedule. Unusable identity/status/revision prevents a safe targeted mutation and returns a structured error; nothing is guessed or repaired automatically.

## Operations, revisions, and conflict flow

Create uses a fresh stable ID and rejects an existing ID even when its row is malformed. Editing keeps the original ID; explicit self-exclusion applies only to that target. SQLite's primary key is the final duplicate-ID safeguard. Never use replacement inserts.

For create/edit/restore, run these steps through the serialized exclusive transaction:

1. Read the current rows and, for edit/restore, check target existence and expected revision.
2. Fully validate the candidate against the approved domain and known dog IDs.
3. Check valid confirmed scheduled intervals with half-open `[start, end)` boundaries. Same-dog overlaps and overlapping training appointments produce warnings; adjacent intervals do not. Other dogs may share boarding/daycare times.
4. Report invalid rows separately. A valid candidate may still be saved after explicit acknowledgement of known warnings and incomplete checking. If diagnostics have changed since review, return a fresh review result without writing. Never keep a transaction open while awaiting user input.
5. Write the booking and corresponding history event atomically, then publish a fresh committed snapshot.

Cancellation checks stable identity, Confirmed status, and expected revision only. It must not require a known dog, schedule parsing, or full booking validation. Update only status, revision, and the updated timestamp; preserve all other stored fields and capture raw before/after snapshots. A valid Confirmed → Cancelled transition therefore works for incomplete schedules and unavailable dogs.

Restoration checks Cancelled → Confirmed, performs full validation and fresh conflict checks, and writes atomically. An invalid cancelled row cannot simply be toggled to Confirmed. It stays cancelled with structured validation errors; repair UI and automatic repair are deferred. No record is deleted by these operations.

Edit/cancel/restore use a conditional UPDATE matching ID and expected revision and increment revision once. Zero affected rows causes rollback and a stale/not-found result, not an overwrite. Preserve the unsaved draft, reload the current record, and revalidate/recheck before another save. No automatic merge or force-save policy.

### Exact wording for later UI integration

Persistent notice:

> Some stored bookings could not be checked. Scheduling conflicts may be missing.

Show a read-only list of affected record IDs and understandable issues. No repair action is promised in v0.5.

Create/edit acknowledgement:

> This booking is valid, but some existing bookings could not be checked. Other scheduling conflicts may exist. Save anyway?

Actions: **Back to review** / **Save anyway**. For restoration, use **Restore anyway** and replace “Save anyway?” with “Restore anyway?”. Keep the persistent notice after saving.

Known conflicts:

> Potential scheduling conflicts found. Review the overlapping bookings before saving.

Stale revision:

> This booking changed since you opened it. Your changes have not been saved. Reload the latest booking and review your changes.

Action: **Reload booking**. These are proposed integration semantics for review, not UI implementation in this task.

## Minimal atomic booking history

| Column | Rule |
|---|---|
| `event_id` | SQLite-generated `INTEGER PRIMARY KEY`; no external retry/idempotency key. |
| `booking_id` | Required FK to `bookings.id`, deletion restricted. |
| `event_type` | `create`, `edit`, `cancel`, or `restore`. |
| `revision_before` | Null for creation; otherwise the prior revision. |
| `revision_after` | New revision; unique with booking ID to prevent two events for one revision. |
| `occurred_at_utc` | Mutation timestamp, distinct from New York booking times. |
| `before_snapshot_json` | Null for creation; otherwise the stored row before mutation. |
| `after_snapshot_json` | Required stored row after mutation. |

Snapshots preserve scheduled and actual fields, including null or malformed content when cancelling. Use a documented versioned snapshot envelope; unexpected SQLite value types need lossless serialization (for example tagged binary values), or the operation must fail and roll back rather than discard content. Snapshot serialization does not call canonical validation.

The row change and its history insertion share one exclusive transaction. If either fails, neither commits. Creation and each seeded booking get a create event at revision 1; edit/cancel/restore each get exactly one event for their new revision. Rejected/stale/rolled-back commands create no successful event. History is append-only by repository convention, not enforced by triggers or a tamper-proof audit system. No history-event retry infrastructure or event sourcing is needed; after uncertain completion, reload current state instead of blindly replaying a mutation.

## Migrations, seeding, and unsupported schemas

Use ordered, immutable migration definitions under `src/storage/migrations/`, preferably TypeScript modules with SQL strings to avoid a bundling loader. Standalone SQL source is permitted only in that designated directory by repository privacy rules. The first migration creates all four tables including history.

Validate that ledger versions form a known contiguous sequence. Apply each pending migration and its ledger entry together in an exclusive transaction. Failed upgrades roll back; migration code never seeds by assumption or silently rewrites applied versions. The minimal ledger cannot detect edited historical migration source: review discipline and upgrade regression tests must enforce immutability.

After migration, transactionally insert the nine validated converted fixtures, their nine create history events, and the seed marker. Seed only when its key is absent. Unexpected ID collisions roll back everything rather than overwrite or ignore rows. Subsequent starts never reseed or undo edits/cancellations. Clients and dogs are neither inserted nor copied into SQLite.

## Timezone verification: mandatory before SQLite implementation

First verify the existing pure New York resolver in the iPhone 16 Pro simulator with the installed SDK 57-compatible Expo Go/Hermes runtime. This gate must pass before installing SQLite or implementing persistence, not merely before screen integration. A separately approved temporary domain-only verification harness may be used; this documentation task adds none.

Record runtime versions, device zones, synthetic inputs, and expected/actual instants or structured errors. Test ordinary winter/summer dates, midnight, years 2000 and 2100, out-of-range years, and device zones New York/UTC/Los Angeles. Verify March 8, 2026 `02:30` rejects as `nonexistent_time`, November 1, 2026 `01:30` rejects as `ambiguous_time`, 47-/49-hour stays across DST, and adjacent same-day checkout/check-in. Check actual observations separately. No device-zone fallback or silent normalization is allowed. If native Intl behavior differs, stop and review the runtime/dependency choice.

After this gate and approved SQLite implementation, independently verify native SQL round trips, restart persistence, rollback, revisions, and history. Node SQL tests cannot replace native verification.

Dashboard and Calendar must calculate **today using `America/New_York`, never the device timezone**. Daily Schedule and every shared “today” selector must use the same zone-aware helper. Refresh on app resume and New York midnight rollover, including after device-zone changes. Dates remain `YYYY-MM-DD` and times `HH:mm`; UTC is reserved for audit timestamps and derived conflict instants. Supported booking years remain 2000–2100. Preserve inclusive checkout-day calendar visibility separately from half-open conflict intervals.

## UUID generation and SQL testing

Use `Crypto.randomUUID()` from `expo-crypto` for new booking IDs; it generates UUIDv4 and is included in Expo Go. Later add it through `npx expo install expo-crypto` alongside SDK-compatible SQLite. Existing fictional IDs remain unchanged. Inject the generator at the service boundary for deterministic tests; do not import Expo into pure domain modules. No third-party UUID package is needed. [Expo SDK 57 Crypto documentation](https://docs.expo.dev/versions/v57.0.0/sdk/crypto/#cryptorandomuuid)

Use Node's built-in test runner and `node:sqlite` `DatabaseSync` with in-memory databases and temporary files for reopen tests. Target Node 24.x (current local runtime: 24.14.1), documenting this test runtime requirement later. No extra npm SQL test dependency is required. Execute the actual migration SQL and repository statements through a small test adapter; transaction tests must use real SQLite rollback, not mocks. Keep SQL to syntax supported by both test and Expo SQLite engines and verify native behavior separately. [Node SQLite documentation](https://nodejs.org/api/sqlite.html)

Cover migration upgrades/rollback/newer schemas, exact seed conversion, seed reruns/collisions, row mapping, duplicate IDs, invalid-row read immutability, malformed/orphan cancellation, failed restoration, conflict completeness, stale revisions, and history rollback. Keep all existing domain/privacy tests. Temporary databases stay outside tracked source paths; no database artifacts are committed. An experimental API warning from a selected Node release must be documented rather than confused with a failing test.

## Privacy, risks, and implementation sequence

Only fictional fixtures, tests, documentation, and screenshots are allowed. Runtime databases, sidecars, history snapshots, exports, and local captures remain protected by repository rules. Never log raw records or matched sensitive values. No real-data importer, Hub access, synchronization, authentication, billing, or approval for storing real customer information is included.

Remaining tradeoffs: relationship/content integrity is application-enforced in v0.5; malformed rows remain until a future reviewed repair workflow; minimal ledgers rely on source review rather than checksum detection; history grows without a retention policy. This is acceptable for a small fictional portfolio database, not a claim of production readiness. The save-with-acknowledgement wording/behavior remains for owner approval. Native timezone evidence is still a prerequisite, not a completed check.

Recommended sequence after architecture approval:

1. Complete the domain-only Expo Go timezone gate before SQLite implementation.
2. Add approved SDK-compatible dependencies, pure row mapping, minimal migrations, and transactional seed/history tests.
3. Implement the adapter/repository and serialized create/edit/cancel/restore services, with invalid diagnostics and stale revisions; verify SQL behavior in Node and Expo Go.
4. Separately approve shared-provider/read integration with New York today and visible warnings; update README, AGENTS, and test documentation.
5. Separately approve booking forms. Identity registry, quarantine, triggers, repair workflows, and editable client/dog tables remain future work.

No implementation, installation, commit, or push is performed by this proposal update.
